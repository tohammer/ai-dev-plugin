# Project audit skill

Status: implemented
Date: 2026-10-05

## Purpose

`/devflow:audit` reviews a whole existing project, typically after
`/devflow:init` adopts it or before larger work starts. It examines
every aspect of the project, not only the code, and turns what it finds
into a dated report and backlog items. Why this is a separate skill and
not a mode of `review`: [ADR 0005](../decisions/0005-whole-project-review-as-separate-audit-skill.md).

Success means:

- One command produces a report covering all aspects listed below, each
  with findings or an explicit "no findings" / "not applicable" /
  "not covered" line.
- Every finding in the report was verified against the code by the
  orchestrator.
- The backlog receives only the items the user confirmed.
- The audit changes no code.

## Scope

In:

- New skill `skills/audit/SKILL.md`.
- `agents/reviewer.md` accepts an area and aspect instead of a diff.
- New docs slot `docs/audits/YYYY-MM-DD.md`, listed in `core.md`, the
  README and `docs/architecture.md`.
- Optional arguments that limit the audit to paths or aspects.

Out:

- Fixing findings. Fixes go through the normal workflow (`spec` or a
  direct change, then `review`).
- Comparing with earlier audit reports.
- A new agent type; the existing agents cover the work.
- `init` creating `docs/audits/`; the audit creates it on first run.

## Design

### Aspects

The skill embeds this checklist. Each aspect appears in the report.

1. **Code.** Correctness, error handling, structure against
   `docs/architecture.md`, dead or duplicated code, needless complexity,
   obvious performance problems.
2. **Security.** Secrets in the repository or its history, input
   handling, authentication and authorisation, unsafe calls, file and
   network permissions.
3. **Tests.** Whether they pass, coverage of the critical paths,
   skipped, disabled or flaky tests, tests that assert nothing useful.
4. **Build and CI.** Whether the project builds from the README's
   instructions, whether CI exists, runs the tests and linters and
   matches the local checks, release or deploy steps.
5. **Dependencies.** Outdated or unmaintained packages, known
   vulnerabilities (running the ecosystem's audit tool where one is
   installed), lockfile present and in use, unused dependencies,
   licences.
6. **Documentation.** README install and usage steps match reality;
   `docs/architecture.md`, ADRs, specs (status, ticked tasks), backlog
   and next-steps match the code; the devflow layout is present.
7. **Configuration and operations.** Configuration handling, logging,
   error reporting, deployment scripts, where the project has them.
8. **Repository hygiene.** `.gitignore`, committed build artefacts or
   large files, licence file, formatter and linter configuration.

### Steps

1. **Scope.** Whole project unless arguments name paths or aspects.
   Record the commit (`git rev-parse HEAD`) and the scope. If the devflow
   layout is missing, offer `/devflow:init` first; without it the audit
   writes only the report.
2. **Baseline.** `devflow:verifier` runs the build, tests and linters
   and reports the results. `devflow:explorer` produces an inventory:
   areas of the code (from `docs/architecture.md` if current, otherwise
   from the tree), CI files, dependency manifests, test locations,
   configuration and deployment files.
3. **Dispatch.** `devflow:reviewer` with a brief naming the aspect, the
   area and files, the baseline results and the aspect's checklist
   entry:
   - Code: one reviewer per area; `model: "opus"` for areas that are
     security- or correctness-critical.
   - Security: one reviewer on `model: "opus"`.
   - Each remaining aspect: one reviewer on the default model. For a
     small project, aspects 4–8 may share one reviewer.
   - Reviewers run in parallel. If the inventory implies more than about
     15 dispatches, propose to the user which areas to cover first.
4. **Verify.** The orchestrator checks every finding against the code
   and drops those that do not hold. A finding is a lead, not a fact.
5. **Rate.** Severity per confirmed finding:
   - critical: data loss, security hole, or the project does not build
     or run;
   - high: wrong behaviour in a main path, missing tests or CI for core
     functionality, docs that make install or use fail;
   - medium: defects in edge cases, maintainability problems that slow
     changes, stale docs;
   - low: cosmetic or minor hygiene.
6. **Report.** Write `docs/audits/YYYY-MM-DD.md` (format below). If a
   report with that date exists, append `-2`, `-3`.
7. **Backlog.** Group related findings into actionable items. Propose
   the items of severity medium and above; the user confirms, removes or
   adds. Write the confirmed items to the backlog (file or directory
   form) with origin `audit YYYY-MM-DD, findings A-n`, the reason and when
   to revisit; mark in the report which findings went to which item.
8. **Hand over.** Summarise the state per aspect, the counts by
   severity, what went to the backlog and what was not covered. Commit
   only if the user asks. The audit changes only docs, so it may run on
   the default branch.

### Report format

```markdown
# Audit YYYY-MM-DD

Commit: <sha>
Scope: whole project | <paths, aspects>

## Summary

The overall state in a few lines; a table of finding counts by aspect
and severity.

## Checks

Build, test and lint commands run and their results.

## Findings

### <Aspect>

- **A-<n>** (<severity>) `path:line` — what is wrong. Evidence or
  failing scenario. Verified by: running | reading. Backlog: <item> | no.

An aspect without findings says "No findings", "Not applicable" (with
why), or "Not covered" (with why).

## Not covered

What the audit did not examine and why.
```

The report is a snapshot; it is not edited after the audit except to
record backlog links in step 7.

### Reviewer agent

The first instruction changes from "Review the diff named in the brief"
to cover either a diff or, for an audit, the area and aspect named in
the brief. The rest of the agent text stays.

### Docs layout

`docs/audits/YYYY-MM-DD.md` is added to the layout block in `core.md`
and the README. `core.md` names `/devflow:audit` in its workflow section.
`core.md` stays at most 70 lines without dropping a rule.

## Error handling

- Build, tests or linters cannot run (missing tool, broken setup): that
  is a finding under Build and CI or Tests; aspects that depended on the
  results say so.
- No CI, no tests, no docs: a finding, not a skipped aspect.
- A reviewer fails or returns nothing usable: re-dispatch once, on a
  stronger model if the first was weaker; otherwise the aspect is listed
  under "Not covered".
- Audit tool for dependencies not installed: assess from manifests,
  note the gap under "Not covered"; do not install tools without asking.
- Project too large for one pass: see the dispatch limit in step 3.
- The user confirms no backlog items: the report is still written.

## Testing

- `tests/run.sh` includes `audit` in the skill checks (exists, name,
  description, at most 100 lines) and still passes; the reference check
  covers `devflow:audit`.
- Headless smoke test in a scratch repo seeded with known problems: a
  bug in a main path, a README install step that fails, a committed
  secret-like string, no CI, a skipped test. The audit must produce a
  report with all eight aspects and catch each seeded problem, and must
  not modify code files.

## Deviations

Added in review, not in the design above:

- Without the devflow layout (init declined), step 7 lists the proposed
  items in the report instead of writing them to a backlog.
- The report never quotes a secret's value, only its location and kind.
- `agents/reviewer.md` also changed its description and opening line,
  and accepts an aspect checklist as a focus.

  `docs/backlog.md`.
