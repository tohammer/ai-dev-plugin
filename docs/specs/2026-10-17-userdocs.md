# User docs skill

Status: implemented
Date: 2026-10-17

## Purpose

`/devflow:userdocs` writes or reworks the user-facing documentation of a
project: the README and, where it outgrows the README, guides and
references in `docs/user/`. It is aimed at technical docs: install,
usage, CLI and configuration. Why a skill and not an agent:
[ADR 0007](../decisions/0007-user-docs-written-by-a-skill-not-an-agent.md);
why `docs/user/`:
[ADR 0008](../decisions/0008-user-docs-beyond-readme-in-docs-user.md).

Success means:

- A reworked README follows the structure below, with a working quick
  start on the first screen.
- Every command in the written docs was run once in this session, or is
  listed to the user as not run, with the reason.
- Every documented command, flag, config key and environment variable
  exists in the code, and every user-facing one in the code is
  documented.
- Design explanation, marketing and FAQ dumps are gone from user docs.
- A README past about 500 lines was checked section by section, and
  the user was told why what stayed is in it.

## Scope

In:

- New skill `skills/userdocs/SKILL.md` with the rules, structure, entry
  format and steps below.
- `docs/user/<topic>.md` in the docs layout of `core.md`, `init` and the
  README; images and recordings in `docs/user/images/`.
- Rules for when and how to use screenshots and recordings, and making
  them where the tools are available.
- `init` loads the skill to write a new README; `wrapup` loads it when a
  change adds a section to user docs or restructures them.
- `doc-checker` checks options in both directions, copy-pastable
  commands and `docs/user/`; `audit`'s Documentation aspect includes
  `docs/user/`.

Out:

- A new agent.
- Tutorials (learning-oriented walkthroughs) and marketing pages.
- API reference generated from code comments (doc generators); the
  skill links to generated reference where it exists.
- Developer docs (`architecture.md`, ADRs, `CONTRIBUTING.md` content
  beyond a link).
- Translation; the skill writes in the language the docs already use.

## Design

### Skill frontmatter

- `name: userdocs`
- `description`: writes or reworks user-facing docs (README, install,
  usage, CLI and configuration reference) to be concise and accurate.
  Use when asked to write, rework, restructure or shorten a README or
  user docs, or when init or wrapup write user doc sections. Not for
  architecture, ADRs or specs.

### Arguments

Optional: `readme`, a path under `docs/user/`, or a topic (for example
`configuration`). Without arguments: the README and all of `docs/user/`.

### Steps

1. **Facts.** Collect from the code, not from the existing docs:
   install method and requirements, commands and `--help` output,
   flags, config file locations and keys, environment variables,
   defaults, precedence. For a broad search dispatch `devflow:explorer`
   with a brief listing these items.
2. **Readers.** Name the audience and the top three to five tasks they
   come for. Ask the user when the code and docs do not show it.
3. **Sort.** Classify existing content as how-to, reference,
   explanation or other. Explanation of design moves to
   `docs/architecture.md` or an ADR, or is deleted; marketing, FAQ
   dumps, changelogs and future plans are deleted (changelog to
   `CHANGELOG.md` if the project keeps one).
4. **Place.** A long, well-structured README is fine. The soft limit
   is about 500 lines: past it, the skill checks every section against
   the reasons below, and if it keeps the README longer it tells the
   user why. Content leaves the README only for one of these reasons:
   - It is for another reader: building from source beyond one command,
     releasing, testing, design → `CONTRIBUTING.md`, `docs/` developer
     docs, or a Development section at the end.
   - It is a feature area that is a guide of its own, with its own
     tasks, options and limits, and longer than the rest of the README
     → `docs/user/<topic>.md`; the README keeps a few lines and the
     link.
   - Users get a binary and never see the repository → one user guide
     (`docs/user/guide.md`, shipped with the release); the README then
     says so in its first lines and serves people building the project.

   The first screen of the README answers what it is, whether it runs
   on the reader's platform, and how to try it, whatever the length.
   An existing user-doc site wins over `docs/user/`.
5. **Write.** Follow the structure, rules and entry format below. Then
   cut: every sentence that the reader does not need for a task goes.
6. **Verify.** Run every command in a scratch directory and compare its
   output with the docs. Do not run commands that install system-wide,
   need credentials, or change external state; list them as not run.
   Compare documented options with the facts from step 1 in both
   directions. Check relative links.
7. **Hand over.** Show the user what moved, what was cut, what was not
   run, and any open questions. Commit only if asked.

### README structure

Sections in this order; leave out those that do not apply:

1. Title and one sentence: what it does, for whom.
2. Optional: a short paragraph on the problem it solves or typical
   uses; key features, one line each; one image or recording if the
   tool is visual (see Visuals).
3. Status: one or two lines on maturity and a support table (platform
   or variant | supported, tested, untested). Not a log of what was
   checked by hand when; that goes to developer docs.
4. Quick start: requirements, the shortest install, the smallest
   working example and its output.
5. Installation: each method or package manager as its own
   subsection, untested ones marked; how to check it worked.
6. Usage: common tasks as short how-tos; a table of commands or keys
   (Key | Command | Action), grouped by purpose.
7. Configuration: where config is read from, precedence (defaults <
   file < environment < flags), a minimal example, the options tables
   or a link to `docs/user/configuration.md`.
8. Limitations: what it does not do, each with the workaround or the
   alternative tool.
9. Troubleshooting: known errors and their fix.
10. Development: commands to build and test, or a link to
    `CONTRIBUTING.md`. The only place for design, ADR, spec and test
    references.
11. License, then credits or disclaimers: last.

A README with more than about eight sections that is read outside a
host that shows a heading outline (a file shipped with a release) gets
a contents list after the introduction.

### Writing rules

Embedded in the skill, condensed:

- Keep how-to, reference and explanation apart; link between them.
- How-to: the title names the task; prerequisites first; numbered
  steps, one action each, imperative; condition before instruction
  ("If you use X, run …"); optional steps start with "Optional:"; one
  method, the shortest; no background, no obvious steps.
- Reference: neutral and complete, one entry format, ordered like the
  product (or alphabetically), no instructions.
- Every command copy-pastable in a code block, placeholders in
  `<angle-brackets>` and explained once; expected output where it
  helps.
- "You", active voice, present tense, short sentences; sentence-case
  headings; code font for anything typed; descriptive link text.
- None of: "simply", "just", "easy", "please", "the following command",
  "above"/"below", marketing, announced future features.
- Write for users, not maintainers: no design rationale, ADR, spec,
  backlog or test-file references, and no warnings addressed to
  developers ("don't reintroduce …") outside the Development section.
- Document what the user can observe and act on, not how it is built.
  Edge cases are spelled out in full only for operations that change
  or delete data; others go to Limitations in one line each.
- Show results as text: expected output in a code block, a rendered
  text UI (a buffer, a TUI screen) as a code block rather than an
  image, a return value inline (`; => "hi"`).
- Performance claims state the conditions (machine, data size, cache)
  and link to how they were measured.

### Visuals

- Use an image or recording only for what text cannot show: a GUI's
  layout, colours and themes, an interaction that unfolds over time.
  A command, its output, configuration or code is never an image.
- A visual tool gets at most one image or short recording near the
  top; further images sit in the section they illustrate.
- Screenshots: cropped to the relevant part, one window size, theme
  and platform across the docs, no personal data (opaque overlay, not
  blur).
- Recordings: one task, under about 30 seconds, no sound needed,
  readable font size. Terminal tools: record from a committed VHS tape
  or asciinema cast. Check that the target host renders the format
  inline (GitHub READMEs: GIF, PNG, SVG, WebP from the repository).
- Every image has alt text saying what it shows (at most about 155
  characters, not "Screenshot of"); the surrounding text carries the
  information too, so the docs work without the image.
- Files go to `docs/user/images/` with descriptive names, kept small
  (a recording of a few MB at most). Each is made by a committed script
  or tape where possible, so it can be redone when the UI changes;
  otherwise the README notes the version it shows.
- The skill proposes visuals and makes them when it can run the tool
  (VHS or asciinema installed, a scriptable GUI capture); otherwise it
  lists them for the user. It never commits a placeholder image.

### Reference entry format

For configuration options, flags and environment variables: one table
per area (Option | Default | Description, plus Type or Allowed values
where they are not obvious from the default), so a reader scans the
area they care about. Where the same setting maps onto several
backends or variants, a column per variant. An entry that does not fit
one row gets its own `###` section with these fields:

```markdown
### `<name>`

<One sentence: what it controls.>

- Type: <type>; allowed: <values or range>
- Default: <value, or "none (required)">
- Also: `--<flag>`, `<ENV_VAR>`
- Example: `<name> = <value>`
- Since <version> | Deprecated in <version>, use `<other>`
```

Lines that do not apply are left out. Notes for edge cases follow the
fields.

### Integration

- `init` step 5: a new README is written with the skill's README
  structure (load `devflow:userdocs`); `docs/user/` is not scaffolded.
- `wrapup` step 2: for a new user-docs section or a restructuring, load
  `devflow:userdocs`; a one-line update is done directly.
- `doc-checker`: adds `docs/user/`, options in both directions, and
  commands that are not copy-pastable (prompt characters, elided
  parts without placeholders).
- `audit` aspect 6: README and `docs/user/` install and usage match
  reality.
- Layout block in `core.md`, `init` and the README gains
  `docs/user/<topic>.md   user docs beyond the README`. `core.md`
  names `/devflow:userdocs` where it lists the other standalone
  commands and stays at most 70 lines without dropping a rule.

## Error handling

- The code cannot be run (missing toolchain, needs a service): verify
  by reading; list every command not run in the hand-over.
- A documented command fails: fix the docs if the docs are wrong; if
  the code is wrong, report it to the user as a bug; the docs describe
  the actual behaviour until the user decides otherwise.
- Docs and code disagree on an option and it is unclear which is
  intended: ask the user; do not pick one.
- The project has an existing user-doc site: write there, keep its
  structure, apply the writing rules and entry format.
- The audience or top tasks are unclear and the user does not answer:
  write for a developer who installs and runs the tool for the first
  time, and say so.

## Testing

- `tests/run.sh` includes `userdocs` in the skill checks (exists, name,
  description, at most 150 lines) and passes; the reference check
  covers `devflow:userdocs`.
- Headless smoke test in a scratch repo with a small CLI (a script with
  two subcommands, four flags, a config file with five keys and one
  environment variable) and a seeded README that has: marketing
  copy, an FAQ section, a design-rationale section with ADR
  references, a dated log of manual checks at the top, a feature list
  with multi-line bullets, a screenshot of terminal output, a flag
  that no longer exists, a config key that is undocumented, and a
  command with a `$` prompt. `/devflow:userdocs` must produce a README in the
  structure above with each seeded problem fixed, run the quick start,
  and report what it moved and cut.
- Trigger check: in a session with the generic `docs` skill available,
  "rework the README" loads `devflow:userdocs`, and "write an
  architecture overview" does not.
