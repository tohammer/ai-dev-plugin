# Ship skill for finishing a branch

Status: implemented
Date: 2026-10-21

## Purpose

No skill takes a finished branch to the default branch. Users finish by
hand, and commits, merge method and PR text vary from run to run.
`/devflow:ship` is the last phase of the feature workflow, after
`wrapup`. It runs the final checks, tidies the commits, writes the PR
description from the spec and the review, integrates the branch the
way the project wants, and cleans up afterwards.

Success means:

- On a project's first ship, the user is asked the shipping policy once
  and it is recorded in `## Shipping`
  ([ADR 0011](../decisions/0011-shipping-policy-in-claude-md.md)); later
  ships do not ask again.
- A branch is integrated only with all checks green, run in that session.
- Commit messages follow the project's convention
  ([ADR 0012](../decisions/0012-commit-convention-detected-not-imposed.md)).
- Nothing is pushed, merged, force-pushed or deleted without the user's
  confirmation of a plan that lists it.
- After a merge, the branch is gone locally and on the remote, and the
  default branch is checked out and up to date.

## Scope

In:

- New skill `skills/ship/SKILL.md`, at most 100 lines.
- The `## Shipping` section: format, the first-run questions, placement.
- Hand-over: `wrapup` points to `ship`; `core.md` adds the step to the
  workflow line.
- README, `architecture.md`, backlog and next-steps updated;
  `tests/run.sh` covers the new skill.

Out:

- `release`: version bumps, changelog, tags. It stays a backlog item;
  ADR 0012 says what it builds on.
- Recording the commit convention (ADR 0012).
- Hosting other than GitHub through `gh`. Without `gh`, ship pushes and
  hands the user the PR text.
- Waiting for CI or reviewers. Ship opens the PR and stops; a later
  run continues.
- Changes to `init`.

## Design

### `## Shipping` in CLAUDE.md

```markdown
## Shipping

- history: squash
- merge: fast-forward
- target: pull request
```

| Key | Values | Meaning |
|---|---|---|
| `history` | `squash`, `keep`, `regroup` | `squash`: one commit for the branch. `keep`: commits as they are. `regroup`: ship proposes a new set of commits (soft reset to the merge base, new commits by topic) when the branch has fixup or WIP commits, else keeps them; the user confirms the grouping. |
| `merge` | `fast-forward`, `rebase`, `merge commit` | `fast-forward`: integrate only if the branch is already on top of the default branch; if not, stop and offer `rebase` or `merge commit` for this run. `rebase`: rebase the branch onto the default branch, then fast-forward. `merge commit`: `--no-ff` merge. |
| `target` | `pull request`, `local merge` | The default. Ship states it and the user can override it per run; keeping the branch is always offered. |

- Placement as for `## Checks`: in `CLAUDE.md`, or in the `AGENTS.md`
  it imports when `## Checks` is there. Never two sections.
- Missing section: ship asks the three questions, one at a time and
  each with explanation, pros and cons and a recommendation. It writes
  the section after the answers, before doing anything else.
- Recommendations to offer: `squash`, since one commit per feature
  matches "docs in the same commit as their code". `rebase`, since it
  gives linear history and does not stop when the default branch has
  moved. `pull request` when the remote is on GitHub and `gh` works,
  else `local merge`.
- Readers accept extra keys, for a later `release`.

### Commit messages

Convention from `CLAUDE.md` if stated, otherwise from the last ~20
commits on the default branch (prefixes, case, mood, body style).
Messages for squashed or regrouped commits: subject in that convention,
body on what changed and why, taken from the spec's Purpose and the
commits being replaced. The attribution lines the harness asks for come
at the end.

### PR description

- Title: as a commit subject in the project's convention.
- Body, short sections: Purpose (one to three lines from the spec),
  Changes (bullets), Testing (checks run and their result, manual or
  smoke checks from the spec), Review (findings fixed, findings
  deferred with their backlog items, if a review report is in the
  session or the spec's Deviations), links to the spec and new ADRs.
- The attribution line the harness asks for, at the end.

### `/devflow:ship`

Frontmatter:

- `name: ship`
- `description`: Integrate a finished branch - final checks, commit
  tidying, PR or local merge per the project's shipping policy, branch
  cleanup. Use when a feature or fix is reviewed and wrapped up, or
  when asked to merge, ship, finish or open a PR for a branch. Not for
  releases or version tags.

Steps:

1. **State.** Current branch, default branch, upstream, working tree.
   - On the default branch: nothing to ship; say so and stop.
   - Uncommitted changes: show them and propose committing them on the
     branch; the user decides.
   - A spec for the branch that is not `Status: implemented`: wrapup
     has not run; offer `/devflow:wrapup` first.
   - An open PR for the branch (`gh pr view`): continue at step 8.
2. **Policy.** Read `## Shipping`; if missing, ask and write it (see
   above).
3. **Sync.** Fetch. If the default branch has moved: `rebase` rebases
   now; `merge commit` merges the default branch into the branch;
   `fast-forward` stops and offers the other two for this run.
   Conflicts: stop, show them, resolve with the user.
4. **Checks.** `devflow:verifier` runs every command in `## Checks`.
   Without the section: determine the commands, say which were used,
   offer `/devflow:init`. Any failure stops the ship; offer
   `/devflow:debug`. A check that could not run counts as not green.
5. **Tidy.** Apply `history`. A rewrite of commits that are already
   pushed needs a force push; the plan says so, and the push uses
   `--force-with-lease`.
6. **Plan.** Show what will happen: the commits that land, the merge
   method, the target, every push, the PR title and description, the
   branches to delete. One confirmation covers the listed steps;
   anything not listed is asked separately. The user may switch the
   target or keep the branch here.
7. **Integrate.**
   - Pull request: push with upstream, `gh pr create` with the
     description, report the URL, stop. Without `gh`: push and give the
     user the title and description to paste.
   - Local merge: merge per `merge` into the default branch, push it if
     it has an upstream.
   - Keep: report the branch state and stop.
8. **Open PR** (later run). Report its state (`gh pr view`: checks,
   reviews, mergeable). On the user's word, merge it with `gh pr merge`
   (`--rebase` for `fast-forward` and `rebase`, `--merge` for
   `merge commit`). If it was merged elsewhere, go on to cleanup.
9. **Clean up** after a merge: switch to the default branch, pull,
   `git branch -d` (never `-D`), delete the remote branch.
   After a local merge, `devflow:verifier` runs the checks on the
   default branch.
10. **Report.** What landed where (commits, PR URL), check results, what
    was deleted, what was not done and why.

## Error handling

- Checks fail or cannot run: no integration; the report names them.
- Rebase or merge conflict: ship stops with the conflicting files and
  resolves them only with the user. It does not drop either side
  without asking.
- Force push rejected by the lease (someone pushed): stop, fetch, show
  the new commits, ask.
- Push or `gh` fails (auth, protected branch, no permission): report
  the error and the state left behind. The branch is untouched beyond
  the steps already done; no retry with `--force`.
- `git branch -d` refuses (not merged as far as git can tell, e.g. a
  squash merge on GitHub): ship verifies the PR is merged, then asks
  before using `-D`.
- `## Shipping` has an unknown value: ship asks for this run and
  proposes the fix to the section.
- No remote: only local merge or keep are offered.

## Testing

- `tests/run.sh`: `ship` in the skill list (frontmatter, 100-line cap,
  references); `core.md` still at most 70 lines.
- `claude plugin validate .`
- Headless smoke tests (see Lessons in `docs/architecture.md`) in a
  scratch repo with a local bare repository as `origin`, a `## Checks`
  section and a feature branch with three commits, one a fixup:
  - First run, no `## Shipping`: the three questions are asked and the
    section is written; with `squash`, `rebase`, `local merge` the
    default branch gets one commit in the repo's message style, the
    branch is deleted locally and on `origin`.
  - A failing check: ship stops before tidying, nothing is pushed.
  - `fast-forward` with a moved default branch: ship stops and offers
    `rebase` or `merge commit`.
- Manual check of the PR path on a real GitHub project: ship this
  feature's own branch with `/devflow:ship` (`target: pull request`),
  then run it again after the PR is merged to see the cleanup.

## Deviations

From the smoke tests and the review, beyond the Design above:

- Step 9 verifies the merge (`git merge-base --is-ancestor`, or PR state
  `MERGED`), then deletes the remote branch before `git branch -d`:
  with the upstream still holding the pre-squash commits, `-d` refused.
- Step 2 commits a newly written `## Shipping` on the branch as its own
  commit, kept out of the tidying.
- Step 1 notes the branch tip; a rejected plan resets the branch to it.
  Declined uncommitted changes stop the ship.
- Step 3 fast-forwards the local default branch to its upstream and
  stops if the branch's own upstream has commits the local branch
  lacks. The force push uses `--force-with-lease=<branch>:<SHA>` with
  the SHA noted in step 3; a plain lease passes after a fetch and
  overwrote a colleague's push in a test. A force push is planned only
  when the branch is pushed again; a local merge never force-pushes.
- Step 5 checks that tidying left the tree unchanged.
- A failed push, `gh` call or lease skips cleanup.
- Step 8 reads the policy first, stops on local commits the PR head
  lacks, checks for `fast-forward` that the PR head contains the base
  tip, and merges only after a confirmed plan.
- One rule covers all questions in the skill: explanation, pros and
  cons, recommendation. The `## Shipping` example block is replaced by
  a one-line format note to stay within 100 lines; the README keeps
  the example.
